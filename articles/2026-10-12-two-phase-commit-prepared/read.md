# 两台数据库都说“准备好了”，为什么还不能各自决定？两阶段提交把一声YES变成承诺

游戏里有一笔交换：甲交出一把剑，乙交出十颗宝石。

如果这两份背包数据都归同一个数据库管，事情很好办——把两处修改塞进同一笔本地事务，要么一起生效，要么一起作废，中间不留半成品。

可游戏做大之后，甲的背包放在东边那台服务器上，乙的背包放在西边那台。两台机器各自都很稳，并不代表这笔交换整体上就稳。

故障来的时候往往是这样：东边查过自己的账，说“剑已经转走了”；西边一查库存，说“宝石不够，交不了”。两台数据库都忠实执行了各自的判断，可合起来看，玩家经历了一场谁也没占到便宜的失败交换。

![两份本地结果无法自动组成整体交换](assets/01-two-local-decisions.png)

麻烦就在这里：一次操作同时落在多个彼此独立的资源上，怎么保证它不会出现“这边提交、那边撤销”的结局？

经典答案叫两阶段提交，英文 Two-Phase Commit，缩写 2PC。它最妙的地方，不在于多问一遍“你到底行不行”，而在于把一句“我行”，变成一种说了就不好反悔的状态。

## 1. 先区分两种“全部完成”

先把三个角色摆上台面：甲库记作 A，乙库记作 B，再加一个协调者 T，专门负责收意见、公布决定。它不替谁看管宝石，也不插手库存本身。

A 和 B 是参与者，论文里常写成资源管理器 RM；协调者常写成事务管理器 TM。这只是逻辑分工，不要求真的凑齐三台物理机器。

![协调者与两个参与者](assets/02-three-roles.png)

本篇盯住两条要守住的规矩。第一，只要有一个参与者最终提交了，另一个就不能最终撤销；第二，已经做出的最终决定，不许再翻回去改写。

这两条并不要求两台机器在同一纳秒里一起改状态。提交消息先到 A、过一会儿才到 B，中间短暂地“A 已提交、B 还在等”，完全可以接受。真正要杜绝的是另一幅画面：A 已经提交，B 却已经撤销。等待和相反结局，是两码事。

![暂时等待与相反决定不同](assets/03-wait-or-disagree.png)

我们还希望等待终究能结束，别让谁永远卡在原地。可“不会作出矛盾决定”和“出了故障还能继续往前走”是两个得分开检查的目标。2PC 最值得慢慢琢磨的，恰好就是它在这两个目标之间划下的那条边界。

## 2. Gray 与 Lamport 问的，不只是多数人同意什么

Jim Gray 和 Leslie Lamport 合写过一篇《Consensus on Transaction Commit》，2006 年发表在 ACM Transactions on Database Systems 上。他们把“事务提交”和“共识”摆到一起比：一笔事务要提交，得所有参与者都点头；某个资源做不到，就不能靠其余资源投票，把它“表决成做得到”。[论文及作者说明](https://www.microsoft.com/en-us/research/publication/consensus-on-transaction-commit/)

![Leslie Lamport本人网站肖像](assets/04-leslie-lamport-original.jpg)

这张照片来自 Lamport 本人的网站，按他公开的任意用途许可收录，不标注成 CC 照片。

![Jim Gray在Tenacious船上，Tony Hey摄于2006年1月](assets/05-jim-gray-original.jpg)

Gray 的照片由 Tony Hey 拍摄，收录在微软出版的《The Fourth Paradigm》里，按 CC BY-SA 3.0 US 使用。两张都保留完整原文件；准确的出处、许可和日期范围写在文末。

Lamport 在论文说明页里回忆过一件事：他和 Gray 曾经一起梳理 Paxos 和传统两阶段提交之间的关系。那是作者对研究过程的回忆，这里照实转述，不当成一段现场对话来写。接下来这篇先顺着他们划清的问题边界理解传统 2PC；Paxos Commit 的完整算法不在这里展开，也不把 2PC 说成这篇 2006 年论文才发明的东西。

再补一句背景：下面出现的角色、剑和宝石，都是本文自设的教学模型，没有真实玩家，也没有真实支付数据。

## 3. YES之前，是“我觉得可以”；YES之后，是“我已经准备承担决定”

假设 A 已经确认剑确实在，B 也确认十颗宝石够用。可光检查一遍还不够。假如 B 发完 YES，转头又让另一笔交易花掉了那十颗宝石，它先前那声 YES 就等于白说了。

所以参与者在回答 YES 之前，得先把本地准备做完：必要的修改、恢复所需的信息、以及对资源的约束，都要可靠地留存下来，让它之后无论按整体决定提交还是撤销，都做得成。至于要留哪些锁、哪个版本、预留多少资源，得看具体系统的设计。

![准备状态背后必须保留的东西](assets/06-prepared-promise.png)

这个状态叫 prepared，本文译作“已准备”。它已经离开随口一说的范畴：既没走到最终提交，也不再是一句能无条件收回的承诺。

换句话说，参与者答的不是“我猜没问题”，而是“我已经把自己锁进一个位置，接下来无论你公布哪个决定，我都做得到”。这句话是有成本的：资源得先占住，别人暂时用不了。也正因为有成本，没人会无缘无故地长时间停在 prepared。

本篇的规矩是——参与者先把“已准备”持久化，再把 YES 发出去。

顺序反了会怎样？如果先发 YES，还没来得及记住自己答应过什么就崩溃了，别的机器可能已经拿着这声 YES 决定了提交，而本机重启后完全想不起来该怎么把这笔操作做完。

![先持久化准备状态，再发送YES](assets/07-before-yes.png)

这跟 WAL 是同一类讲究：关键在先后依赖。只是这里多了一层新含义——日志不光是给本机重启用的，它还要支撑别的机器，凭我这一句答复去做决定。

## 4. 第一阶段：询问，然后等待有分量的回答

按一种常见的叙述顺序走：协调者先向 A、B 发出 PREPARE 请求。

A 收到后完成本地准备，把 prepared 状态持久化，再回复 YES；B 照做一遍。哪一边准备不出来，都可以在发出 YES 之前回一句 NO，顺手撤掉自己那半边。

![请求准备与两个YES](assets/08-prepare-messages.png)

这里有个容易踩的坑：“收到两个 YES”，不能实现成“收到两条文字是 YES 的网络消息”。同一个参与者可能重发答复，网络也可能把同一条消息投递两遍。A 的 YES 来两回，并不能顶替 B 的那一票。

协调者手里得有一份固定的参与者名单，按身份去记谁已经准备。本文用一个集合保存收到过 YES 的参与者编号，A 重复加进去，集合里也还是只有一个 A。

![按参与者身份记票而不是数消息](assets/09-distinct-votes.png)

本篇的模拟器为了把注意力集中在安全性上，省掉了协调者的询问消息，允许每个参与者主动准备。这跟原论文附录里的简化方向一致：询问只是启动准备的提示，真正约束决定的是那份准备承诺。正文画出请求消息，不代表程序测过完整的网络栈或者请求重试。

## 5. 第二阶段：决定先落稳，再让别人照办

一旦协调者收齐了所有参与者的 YES，它就具备了作出 COMMIT 决定的条件。

它先把决定持久化，再通知 A、B。A 收到决定，提交自己那半边；B 收到，也提交自己那半边。为了方便阅读，这里把“持久化最终决定”和“发送决定消息”画成前后两个独立步骤。

![先保存不可反悔的决定，再发送](assets/10-decision-before-send.png)

为什么非要先记稳？设想协调者只在内存里决定提交，先通知了 A，A 提交完成，协调者却崩了。重启之后它要是把“曾经决定提交”忘得一干二净，又因为超时决定撤销 B，整笔交换就裂成了两半。

反过来，只要 COMMIT 决定已经持久化，剩下的活儿就是继续把它传播出去。某封通知暂时送不到，也不能据此把它改判成 ABORT。

![提交通知可以先后到达](assets/11-different-arrival-times.png)

参与者之间这段不同步的时间，还可能影响到外部的读取。2PC 本身管的是原子提交决定；跨库的读者能不能读到一个一致视图，还得靠隔离级别、锁或者别的读取协议来配。本篇不会把“决定不矛盾”偷偷换成“任意查询都能看到全球同一时刻”。

## 6. 有一个NO，为什么不是少数服从多数？

假设 A 能交出剑，B 的宝石却不够。B 在发出 YES 之前拒绝了，协调者就该走撤销路线，通知其余参与者放弃这次交换。

![一边无法准备时的撤销路线](assets/12-no-and-abort.png)

再把模型扩成三方：剑库、宝石库、入场券库。前两方 YES，入场券库 NO。

三分之二同意，也不会让一张不存在的入场券凭空出现。多数票能帮一组副本就同一条记录达成一致，可在原子提交里，每个参与者背后可能是无法替代的资源。

多数票在这里救不了场。

要让整笔事务提交，缺了任何一个必需参与者都不行。

![三个不同资源不能用多数票替代全员准备](assets/16-majority-is-not-all.png)

不过“全部 YES”也不意味着“每个参与者现在可以各自提交了”。它只说明协调者具备了作出提交决定的条件。谁掌握“全员都准备好了”这个事实？最终决定保存在谁手里？出了故障，又由谁拿出证据？这些问题还悬着。

## 7. 最难的状态：我已准备，却听不见决定

A 已经把 prepared 持久化，YES 也发出去了。接着协调者失联，A 左等右等，始终没收到决定。

对 A 来说，至少有两条世界线长得一模一样：

- 世界一：协调者已经把 COMMIT 记稳，只是消息没送到 A。
- 世界二：协调者已经把 ABORT 记稳，只是消息同样没送到 A。

这两条世界里，A 自己的持久状态可以完全一样：prepared、YES 已发、没收到任何最终通知。哪怕 A 和 B 都已准备、都还没收到决定，单看这两份本地状态，也分不出协调者最后到底记下了什么。

![相同本地观察对应两种隐藏决定](assets/13-two-hidden-worlds.png)

在本篇的安全性模型里，协调者还没作出决定时，它有权选择撤销——比如超时策略触发了撤销；它不会因为“对方也许已经准备”就丢掉撤销权。可一旦已经持久提交，就再也不能撤销。

这里双方的地位并不对称：参与者一旦许下 YES，就等于把无条件反悔的自由交了出去。

协调者失去的是时间——它可能得等、得重发、得恢复；参与者失去的是选择权。这两样东西的价钱差得很远，后面的很多工程麻烦都从这条不对称里长出来。

## 8. 超时后自己撤销，会发生什么？

试着给 A 加一条听上去挺体贴的规则：“prepared 等太久就自己撤销，别老占着资源。”

坏事可以这么发生：A 发出 YES，然后等超时，自行撤销；它那声 YES 晚一点才被协调者收齐。协调者没有理由知道 A 偷偷反了悔，于是记稳 COMMIT，通知 B。结果 B 提交，A 已经撤销。

![prepared超时自行撤销的反例](assets/14-timeout-abort.png)

换个顺序也一样糟：协调者早就决定了提交，B 也已经提交，偏偏给 A 的通知一直丢。A 再自行撤销，照样把一致决定破坏掉。

那超时后自己提交行不行？同样不行。B 可能压根准备不了，或者协调者已经决定撤销。prepared 并不等于“成功只差走个过场”，它是一个等待整体决定的状态。

![prepared也不能自行提交](assets/15-local-commit.png)

超时能告诉我们的，只有“等得比预期久”。它告诉不了我们“那台机器的持久日志里一定没有 COMMIT”。

沉默不是证据。

在允许任意消息延迟的安全性讨论里，沉默更不构成相反决定的证明。这条区分有个很实际的好处：它把“我该怎么办”拆成了两个可以分别回答的问题——现在能确认到哪一步，以及在这个确认程度上允许做哪些动作。很多分布式故障处理的混乱，都来自把这两个问题揉成一句“感觉它应该是挂了”。

## 9. 什么证据可以结束等待？

最直接的办法，是等协调者恢复，把持久决定读回来，再重新发一遍。它重启后不能靠已经丢失的内存印象行事。

如果系统实现了合适的结果查询或者终止协议，一个已经知道可靠最终决定的参与者，也可能帮别人问到结果。所以“协调者一坏，所有事务必定永远卡死”同样是过度概括。

![知道最终决定与只有prepared不同](assets/17-ask-for-evidence.png)

真正棘手的情况是：能联系上的人都只知道 prepared，找不到任何可靠的最终决定，也联系不上保留决定的那个协调者。这时经典 2PC 可能阻塞。它宁可继续等，也不肯随手造出一个跟隐藏决定打架的新结果。

注意，“可能阻塞”并不等于“安全性失效”。算法依然能保证没有人作出相反决定，只是在这样一个故障场景里，它没法保证参与者及时收场。

![恢复依赖持久状态，不靠猜测](assets/18-restart-from-record.png)

当然，本篇的前提是持久记录还读得回来。要是决定日志所在的介质彻底毁坏，或者某个进程重启后冒充另一个协调者乱发消息，那就超出了这个故障模型。加副本、选主或者上共识机制，确实能改变某些可用性条件，但那需要明确的新协议，不是把协调者进程多开一个就算解决。

## 10. 一句超时处理，可以暴露整个理解是否正确

下面这段只是一张状态规则表的代码表达，没有网络，也没有数据库操作：

```python
def timeout_action(state):
    if state == 'W':
        return '可在承诺前撤销'
    if state == 'P':
        return '等待或查询可靠决定'
    return '保留已有最终结果'
```

W 表示还在工作、尚未承诺 YES；P 表示已准备；C 和 A 分别是最终提交与撤销。最后一行只接受本篇这四种状态，不是通用的输入校验。

三个分支连起来看，它其实在说一件很朴素的事：**能自己拿主意的窗口，在发出 YES 那一刻就关上了。** 关窗之前，撤销是免费的；关窗之后，撤销需要证据。

![四种状态对超时的不同含义](assets/19-timeout-state-table.png)

这个小函数不负责执行恢复，它只想提醒一件事：同样叫“超时”，落在承诺之前和落在承诺之后，允许的动作完全不同。工程上不能把一个统一的“超时就回滚”回调，糊在所有阶段上。

## 11. 我们怎样实际寻找反例？

配套的[两阶段提交模拟器](examples/two_phase_lab.py)显式保存了五类信息：参与者状态、谁发出过 YES、协调者收到谁的 YES、持久的最终决定，以及决定是否已经发出。

准备持久化和发送 YES 是两个动作；决定持久化和发送决定也是两个动作。正因如此，程序能够停在“已经落稳、但还没发消息”的那道缝里。

![枚举器保存的五类状态](assets/20-model-state.png)

模拟器把每一种允许的下一步都枚举一遍，记下出现过的不同状态。它用的是“曾经发送过的消息集合”，不把消息拿走：接收可以任意推迟，也可以一直不发生；重复消息不会多出第二张选票。这是一套安全性模型，不是一份承诺消息必达的网络实现。

节点崩溃在这里被抽象成暂停动作，恢复后从同一份持久状态接着走。文件损坏、冒名消息、磁盘写到一半，这些都没模拟。既然允许永久暂停，也就没有偷偷假设协调者一定按时回来。

对 1、2、3、4 个参与者，实际分别枚举出 20、104、602、3668 个状态，合计 4394 个；检查每一步都不会让已经结束的状态发生反转，也没有出现任何“有人 C、有人 A”的状态。

![实际安全性枚举与三种错误改法](assets/24-test-results.png)

接着分别故意塞进三种坏规则：prepared 超时自行撤销、prepared 自行提交、协调者凭多数 YES 提交。三种都实际找到了有限反例，程序会打印完整的事件序列；前两种用 2 个参与者就能暴露，最后一种要用 3 个。

当然，作者这份有限枚举不是一般正确性证明。更重要的理由是结构上的：只有持久化 prepared 之后才能发 YES；发过 YES 的参与者不再自行撤销；协调者只有收齐所有身份的 YES 才能提交，而且最终决定只允许作一次。于是只要有人最终提交，其他参与者要么还在等同一个提交决定，要么也已经提交，不可能合法地走进撤销。

## 12. 真实数据库里的prepared，会占着什么？

PostgreSQL 18 提供了 `PREPARE TRANSACTION` 这类接口，供外部事务管理器组织跨资源的事务。官方文档也把话说得很直白：prepared 事务仍然持有原来的锁，长时间遗留会造成实际问题；这个接口并不是在鼓励应用随手留下待决事务。[官方文档](https://www.postgresql.org/docs/18/sql-prepare-transaction.html)

![准备状态在真实系统中可能继续占用资源](assets/21-real-prepared-cost.png)

所以“阻塞”不只是屏幕上转个圈那么轻。被占住的行、锁或者预留资源，可能让后续相关操作一起跟着等。一次协议里的等待，会顺着资源依赖传给下一个操作。

本文没有连接 PostgreSQL，没有创建真实的 prepared 事务，也没有给出生产环境的清理命令。面对一笔真实的待决事务，光看到一个很旧的编号就手动撤销，等于在不知道整体决定的情况下替系统反悔。正确的做法是先查清负责这笔事务的管理器和可靠的最终决定。

## 13. 三组容易混淆的词

第一组，2PC 与两阶段锁 2PL。前者协调的是提交还是撤销这个整体决定；后者属于并发控制，讨论的是锁什么时候拿、什么时候放。名字里都带着“两阶段”，彼此却不能互相替代。

第二组，原子提交与隔离。原子提交防止参与者作出相反的终局；隔离约束的是其他事务怎样观察、怎样干扰执行过程。具体数据库常常让两者配合工作，但一个协议名不会自动替另一层许诺全部性质。

![原子提交与隔离是不同问题](assets/22-commit-and-isolation.png)

第三组，2PC 与共识。共识可以用来复制协调决定，也可以被组织进更复杂的提交协议里；但“多数副本达成一致”并不等于“所有业务资源都已准备”。Gray 和 Lamport 的论文，正是先把这些角色分清楚，再去分析它们之间的关系。

![两个阶段与两类协议不要按名字混同](assets/23-not-the-same-question.png)

这篇没有展开三阶段提交，也没有声称多加一个阶段就能在任意网络分区下解决等待。要下这种判断，得先把时间、故障、成员和恢复这几项假设重新说明一遍。

## 14. 最后一封信没到，故事还没有结束

做个小练习：A、B 都已准备，协调者已经把 COMMIT 记稳，刚通知完 B 就崩了。B 提交了，A 还停在 prepared。

现在 A 等了十分钟，它能自行撤销吗？不能。时间再长，也不会把 B 已经完成的提交变成没发生。

那如果协调者恢复过来，读到了 COMMIT，该做什么？继续把同一个提交决定传播出去，别重新发起一轮多数投票。

![最后练习：一边提交，一边仍等待](assets/25-final-exercise.png)

下图把正常路径的持久状态和消息步骤逐一展开。它取自配套程序里 11 个真实状态；动画间隔只是为了方便阅读，不代表网络耗时。

![正常两阶段提交的11个离散状态](assets/26-normal-animation.gif)

两阶段提交留给我们的，是一种很具体的克制：承诺之前，可以说不；一旦给出有持久证据的 YES，后面的行动就必须拴在同一个整体决定上。

它没有让故障消失，也没有让沉默变成知识。它把最危险的那句“我猜应该没事”，换成了三个可以追问的问题：你现在处在哪个状态？你已经对别人承诺了什么？最后决定的可靠证据在哪里？
