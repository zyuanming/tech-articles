## 本文实际运行的实验

`examples/run_model.py` 只用 Python 标准库，环境记录见 `examples/run-environment.json`。默认集群 5 台，单向消息延迟 1 秒，心跳间隔 8 秒，选举超时 15–30 秒随机，模拟步长 0.5 秒。

### 关键结果

| 项目 | 结果 |
|---|---|
| 固定选举超时（全部 20 秒） | 600 秒内每台发起 30 次选举，任期涨到 30，**始终没有领导** |
| 随机选举超时（40 个种子） | 首个领导出现在 17.5–26.5 秒，平均 19.79 秒，**0 次失败** |
| 一次客户端写 | 从发出到提交 2.0 秒，16 条消息（一个来回） |
| 集群规模对延迟 | 3 / 5 / 7 台的提交耗时都是 2.0 秒；每条写的消息数 5.6 / 11.2 / 17.7 |
| 领导崩溃 | 16.5 秒后选出新领导（任期 2），日志与旧领导一字不差 |
| 日志冲突修复 | 跟随者的两条未提交条目被截掉，替换为新领导的条目 |
| 网络分区 | 多数派 16.5 秒后选出任期 2 的新领导；被隔离的旧领导仍是「领导」，接受 2 条写请求但 commitIndex 停在 2 |
| 分区恢复 | 旧领导退位，那两条孤儿条目被丢弃，从未提交 |
| Figure 8 反例 | 正确规则提交到索引 1；错误规则提交到索引 2，随后 `T2:b` 被覆盖 |
| 成员变更 | 5 → 6 → 7 台，过半 3 → 4 → 4，新节点每次都追平现有日志 |
| 随机日程（400 个 × 400 秒） | 4437 次崩溃、4036 次重启、1704 次分区、3962 条写请求，**0 次违规** |
| 提交规则改错后 | 同一批随机日程**仍然 0 次违规**（随机测试抓不到） |
| 跟随者回复改错后 | 400 个日程里 1 次违规（种子 62）；改回正确写法后 0 次 |

### 写作过程中实际发现并修好的一个 bug

第一次跑完 300 个随机日程，检查器报告 1 次违规（种子 62），命中的是**状态机一致性**（`check_safety` 的第 4 条）：**B 与 E 已应用的序列不同**。

具体状态：两台机器最终的日志完全相同、`commitIndex` 都停在 8，但索引 1 上 B 执行的是 `cmd0`，E 执行的是 `cmd7`，而 `cmd7` 后来被日志修复覆盖，最终任何一台机器的日志里都不存在。也就是说，E 执行了一条**从未被任何多数派验证过**的命令。

排查结果：跟随者在 `AppendEntries` 成功回复里写的是 `self.last_index`（自己整份日志的长度），而不是 `prev_index + len(entries)`（本次核对到的位置）。后果是领导收到一个**大于本次发送范围**的数字，误以为对方早已拥有自己还没复制过去的条目，把一条并未真正达成多数派的条目提交了。

改成 `prev_index + len(entries)` 之后，同一批日程 0 违规。为了可复现，模拟器保留了开关：`Cluster.reply_rule = 'whole_log'` 会故意用回错误写法，`raft.safety_sweep(400, reply_rule='whole_log')` 能在种子 62 上重现它。

### 检查器本身也改过一次

第一版的「已提交条目」检查是：只要某台机器提交了索引 k，**任何**机器在索引 k 上的内容都必须相同。这条性质**过强**——一个被困在少数派分区里的节点，完全可以在某个索引上持有冲突的、未提交的条目，这并不违反 Raft 的安全性。检查器因此报告了两处假阳性。

改成了 Raft 真正保证的性质：**两台都提交了同一索引 k 时，它们的内容必须相同**（由「两个多数派必然相交」推出）。同一批日程随后 0 违规。

## 明确没有做到的事

- 没有查阅 Raft 论文原文的措辞与页码。正文用通行编号「Figure 8」指认那张反例图，但没有核对它在论文中的位置；它的状态是照抄该图内容手工构造的。
- 没有实现持久化：模拟器里的日志、任期与投票记录都在内存中，没有建模「先落盘还是先回复」的顺序问题。真实实现里这是最容易出错的地方之一。
- 没有实现日志快照与压缩，因此日志在模拟中无限增长。
- 没有实现批量复制、流水线复制、只读请求优化（ReadIndex / 租约）、Pre-Vote、CheckQuorum、单节点成员变更之外的联合配置。
- 没有建模磁盘故障、消息重复投递、消息乱序到达、时钟漂移。模拟器的消息队列是先进先出，所有消息延迟相同。
- 没有对任何真实 Raft 实现做过测试或对比。
- 随机日程的安全性检查不是证明：它只说明「在这些日程里没抓到违规」。Raft 的正确性依据是论文中的归纳论证，本文没有重述该论证。
- 没有测性能：正文的「2.0 秒提交」是模拟延迟下的结果，不是任何真实系统的实测数据。
