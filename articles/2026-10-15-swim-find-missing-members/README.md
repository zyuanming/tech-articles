# SWIM教学材料：可重放模型与真实本机UDP

正文：[read.md](read.md)。本目录有两种不同实验，不能把虚拟毫秒与真实运行耗时混用，也不是可直接部署的成员管理软件。

## 1. 确定性的离散事件模型

Python 3.12.14，只有标准库依赖。运行：

```sh
python3 examples/run_model.py --output swim-model-run-02
```

输出目录必须尚不存在；程序不联网。输出四个数据文件和stdout.txt。本次保存的[results.json](examples/results.json)、[events.csv](examples/events.csv)、[gossip-contacts.csv](examples/gossip-contacts.csv)、[merge-tests.json](examples/merge-tests.json)与[标准输出](originals/model-stdout.txt)可逐字节比较。

时间单位是虚拟毫秒。成功消息每跳20；首次直接等待100；一次探测总窗口300；首次进入某一版怀疑后再等600。用堆维护事件，时间相同时按插入顺序执行。模型不会睡眠，也没有实际网络延迟。六个节点A至F的成员表仅维护关于B的一条记录，初态为Alive、incarnation 0。

四个独立场景分别从空事件队列和初态重置：

- healthy：A在0探测B；40收到直接ACK，共2次发送。
- indirect：A与B之间的消息在接收事件被注入丢弃；100请求C、D；180收到首个转发ACK，共9次发送。
- pause：B在虚拟时间350前无法处理收到的包；300时A怀疑B；400安排A探测C，440安排C探测B，500安排C探测A。460时B在PING中看到关于自己的怀疑，提升自己的incarnation至1；520时A收到搭载的Alive 1。560时额外向A的合并函数注入一个过时Suspect 0，用于验证迟到更新，不冒充一次真实网络发送。900时旧怀疑计时器不再适用。
- dead：B始终无法处理包；后续联系计划同pause。A在300怀疑、900确认。C自己的怀疑从420开始，于1020确认。模型未安排将确认传播至所有六人，也不声称全组收敛。

这个固定联系计划故意让一个读者能逐步算出反驳路径；它不是SWIM完整的每成员周期调度。模型不包括加入/退出、身份认证、重加入、崩溃恢复、恶意节点、更新队列与有限传播预算、网络分区修复、完整成员表及生产实现附加机制。

Alive/Suspect的合并按版本、同版本怀疑优先。Confirm采用2002年原论文的终态语义，不让普通Alive复活同一已确认成员身份。只在首次进入一版怀疑时启动计时器，收到重复怀疑不重新开始。被怀疑的B只能自行提升B的incarnation。所有这些边界都不能由一个通用字符串排序自动代替。

独立的传播子实验只处理一条更新：六成员、每轮每人均匀独立选一个其他成员、无丢包、PING/ACK都可携带更新、Python random.Random(2301)。各联系人读取轮初状态，ACK可携带刚从这次PING获得的更新，新知识在轮末合并。它记录8轮，共48次联系，人数为1、2、4、6、6、6、6、6、6。这是分离出来的传播教学模型，不是上面四个探测案例的后续。

原始事件CSV含102个数据行；另有表头。数字计数与概率使用整数及fractions.Fraction计算，JSON的概率字段转为浮点展示。概率公式的假设是N人中恰好1人停止，余下N−1人各从N−1个其他成员独立均匀选择；不能拿它估计相关网络故障。

## 2. 实际localhost UDP实验

```sh
python3 examples/run_udp.py --output swim-udp-run-02
```

无需第三方库。此程序确实创建六个UDP套接字，绑定127.0.0.1的临时端口，仅本机通信，结束后关闭。A、B、C、D参与这次探测；E、F保留为六成员配置但本次不接收探测。三个场景各自重新创建套接字，只有一个Python进程，没有六个独立服务进程，也没有使用pcap抓包。

计时由time.perf_counter_ns给出，以每个场景开始为零点；记录小数毫秒。每次套接字收到包以后，应用调度20毫秒后处理它。100毫秒后若未成功则请求C、D帮忙；约300毫秒检查结果。时间会受调度影响，不能要求后续运行与本次毫秒数逐字节一致。

故障注入发生在应用处理层：indirect忽略发送端与接收端是A/B这一对的报文；silent忽略所有发给B的探测。本次所有sendto发送均有SOCKET_RECEIVE记录，APP_DROP是应用丢弃，不能称为物理链路丢包。第三种场景不会产生ACK，因此发送2+2+1＝5包；正常2包；两帮手成功9包。

本次[59行原始应用事件](originals/udp-events.csv)、[结构化结果](originals/udp-results.json)、[stdout](originals/udp-stdout.txt)保留未人为修整的计时。正文展示四舍五入到0.1毫秒的40.6、182.0与300.4。

重复实验检查的是分支、发送/接收/应用丢弃计数和是否在窗口内得到ACK。负载很高的机器可能使这些时间条件失败；这意味着本次实验条件不满足，不应修改日志伪造通过。

## 3. 断言覆盖

- 直接和间接首个ACK分别为虚拟40、180毫秒。
- pause中A的状态改变为300怀疑、520恢复；900旧定时器取消。
- dead中A为300怀疑、900确认。
- 同代Alive不取消怀疑；更高代Alive可取消未确认的怀疑；旧Suspect不可使新Alive倒退。
- Confirm终态不可用普通Alive覆盖。
- 三条更新全部六种排列最终都为Alive 1。
- 同代重复怀疑不把原定900的确认延后。
- 一条更新的固定种子传播最终覆盖六成员。
- 实际UDP三个案例分别发送/收到2、9、5个报文，应用丢弃0、1、3个；前两个有ACK、最后一个没有。

这些是明确输入下的代码检查，不是完整协议正确性证明，也不验证任意调度、分区或安全性。

## 4. 重绘

```sh
python3 examples/build_figures.py
```

需已经安装Pillow与Noto Sans CJK Regular/Bold。本次Pillow 12.3.0，字体集合index=2；脚本不安装软件或下载素材。原图宽1062像素，所有文字至少38像素，在354像素显示宽度下有效字号至少约12.67像素。图内标签均做画布边界检查，实际手机比例仍需视觉核对。
