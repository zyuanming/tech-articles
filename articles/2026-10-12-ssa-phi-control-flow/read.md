# 变量只能赋值一次，循环怎么还能转？SSA给每个值一个清楚的来处

看一眼这三行小程序：

```text
score = 10
score = score + 3
result = score * 2
```

人读起来不难：最后得到26。可是第二行左右两个score，指的不是同一个时刻的值。右边拿旧分数，左边写新分数。

再加上几十个分支、几层循环，编译器若想问“这个乘法到底用了哪一次计算的结果”，就不能只看变量名字了。它得沿着程序所有可能走过的路，找出这个名字究竟指向谁。

![同一个score名字，在三行程序里先后指代两个值](assets/01-same-name.png)

能不能换一种写法，让每个值的来源天然更清楚？

一种经典做法叫SSA，Static Single Assignment，中文常译为静态单赋值形式。听上去像一条不近人情的禁令：一个变量只能被赋值一次。

可程序明明要循环，分数明明会变化。这条规则到底管的是“代码长什么样”，还是“机器运行时发生了几次”呢？

## 1. 先换名字，不改结果

把刚才的程序写成：

```text
score0 = 10
score1 = score0 + 3
result0 = score1 * 2
```

每个新名字在左边只出现一次。最后仍是26，只是10和13不再共用同一张名牌。

![重命名后，每个计算结果拥有独立名字，后续使用明确写出来源](assets/02-renamed-values.png)

这里的0、1不是数组下标，也不是程序执行到第几秒。它们只是用来区别定义的标签。编译器完全可以改用其他不重复的名字。

我们把“在代码中产生一个值的位置”叫定义，把“拿这个值去做事的位置”叫使用。SSA希望让每个名字只有一个定义点，使用者能直接找到它。

![定义与使用关系，和原代码逐行执行顺序是两种不同的信息](assets/03-def-use.png)

这并不要求计算机为每个名字永久留一块独占内存。SSA是一种中间表示，也就是编译器分析、修改程序时使用的内部写法。最终哪些值放进哪个寄存器、能不能复用同一块存储，还要由后面的阶段处理。

我们暂时只谈整数值，不谈指针、数组和多线程。把边界缩小，才能先看清名字本身的作用。

## 2. 一次关于“改名”的研究，怎样连到了程序的岔路

1980年代，Jeanne Ferrante与同事研究程序中的重命名。她在2006年UC San Diego的一篇报道中回忆，自己在1985年到UC Berkeley访学期间研究了这个方向，回到IBM后，与Ron Cytron合作撰写了1987年的《What's in a Name》。与此同时，Barry Rosen、Mark Wegman、Kenneth Zadeck等人在探索更有力的程序变换，两条研究线逐渐结合。[大学原报道及人物照片](https://jacobsschool.ucsd.edu/news/release/547?id=547)

这段历史里有一个很具体的转折：Ferrante回忆，她意识到先前研究控制依赖时用过的思路，可能也能帮助构造SSA。这里是多年后、具名的研究者回忆，不是我们补写的实验室对话。

![重命名和控制路径两类问题，在SSA构造研究中相遇的历史问题图](assets/04-history-questions.png)

1989年的会议论文已有这项高效构造工作；1991年，Cytron、Ferrante、Rosen、Wegman、Zadeck的长篇论文把SSA与控制依赖图的构造放在一起讨论，使用了支配边界这个概念。[1991原论文](https://www.cs.utexas.edu/~pingali/CS380C/2010/papers/ssaCytron.pdf)

重要的不只是“换个名字好看”。一种表示方式如果很有用，却很难从普通程序造出来、或者一造就膨胀得很大，工程师也不容易采用它。构造成本本身，就是这篇论文要解决的实际难题之一。

我们先用一个小分支，看看难点为什么会出现。等走到循环，再回头理解“支配边界”这个有点吓人的名字。

## 3. 直路上好改名，岔路口怎么办

假设游戏根据一个真假条件flag，选择不同的奖励：

```text
if flag:
    x = 3
else:
    x = 1
return x + 2
```

flag为真，结果是5；为假，结果是3。

给两次赋值起不同名字，左路叫x1，右路叫x2。问题马上来了：两条路重新汇合后，该写“x1+2”还是“x2+2”？

![奖励程序的左右分支分别定义x1和x2，汇合后还缺一个明确的名字](assets/05-branch-puzzle.png)

不能都用x1，因为走右路时x1根本没有产生。也不能取平均；那会把本来的5或3变成另一种结果。

更不能把“如果走左路就用x1，否则用x2”的信息藏进人的脑海里，让编译器自己猜。我们需要在中间表示中，明确记下这件事。

## 4. phi不是算术函数，是“从哪条路来的”登记处

先给几段代码所在的位置起名字：entry是入口，left是左路，right是右路，join是汇合点。

我们把join里的选择写成：

```text
x3 = phi(left: x1, right: x2)
y1 = x3 + 2
return y1
```

phi读作希腊字母φ的名字。这里先把它理解成一张来路表：**刚从left进入，就取x1；刚从right进入，就取x2。**

![phi把前驱代码块与对应值成对记录](assets/06-phi-arrival.png)

它不是把x1和x2都计算一遍，也不是让两条分支同时执行。真正运行时，只走过其中一条路径，phi接下那条路径提供的值。

![同一份phi写法，在两次不同运行中分别选择3和1](assets/07-two-executions.png)

这样，x1有一个定义，x2有一个定义，x3也有一个定义，就是这条phi指令。后续使用只要找x3，便能找到唯一的定义点；定义点内部再把不同来路列清楚。

“唯一来源”并没有抹掉路径差异，而是把差异收进了一个明确的位置。

## 5. 基本块：一段进来就顺着走到底的路

我们刚才给entry、left、right、join起了名字，它们就是这个例子里的基本块。

可以把基本块理解成一段中途不分叉的指令序列：从块开头进入，按顺序执行，最后决定下一步去哪，或者返回结果。用箭头连接可能的跳转，就得到控制流图，简称CFG。

![四个基本块和它们的跳转，组成一个菱形控制流图](assets/08-cfg-blocks.png)

别把两种箭头混在一起：

- 控制流箭头说“执行完这一块，可能去哪里”。
- 定义—使用箭头说“这条运算拿的是哪个值”。

它们经常画在同一份程序上，却回答不同的问题。

![控制流跟着路径走，数据关系跟着值的来源走](assets/09-two-kinds-arrows.png)

在LLVM 18.1.8的规则里，phi放在基本块开头，并为前驱基本块列出对应的输入值。它选取刚刚执行完的前驱所对应的值；每个输入值的使用，被视为发生在那条进入当前块的边上。[固定版本phi说明](https://releases.llvm.org/18.1.8/docs/LangRef.html#phi-instruction)

“值与前驱要成对”并非装饰。如果把左右标签接反，程序仍可能跑起来，却会在错误的分支给出错误奖励。

## 6. 为什么不能把左路的值直接拿到汇合处

这时可以介绍一个很直观的图论词：支配。

如果从入口出发，无论走哪条能到达B的路，都必须经过A，就说A支配B。这里讨论的是代码图中的所有路径，不只是刚才碰巧运行过的那一条。

![入口支配汇合点，但左路并不支配汇合点，因为还能绕右路到达](assets/10-dominance.png)

在奖励程序里，entry支配join。left却不支配join，因为entry→right→join绕开了left。

普通指令使用一个SSA名字时，它的定义必须在所有到达这次使用的路径上已经发生；同一块内，也要先定义再使用。这就是定义应支配普通使用的直觉。

所以join直接写x1+2不合法，而使用phi产生的x3就合法。phi的左输入x1只需在left→join那条来边上可用；不能要求左路定义先经过右路。

![普通使用要求定义覆盖所有来路，phi输入只对应它自己的来边](assets/11-edge-use.png)

我们的教学检查器会直接拒绝“join用x1+2”这种版本。即使你只拿flag=true测试，它看起来每次都对，也不能证明另一路安全。

## 7. 循环没有毁掉SSA，反而让phi更有用

现在把条件奖励换成累加：算0+1+…+(n−1)。普通写法是：

```text
i = 0
s = 0
while i < n:
    s = s + i
    i = i + 1
return s
```

n=4时，返回6。

循环头有两种来路：第一次从entry进来，此时i、s都应是0；以后从body绕回来，此时要接住上一轮产生的新i、新s。

![循环头的两种来路：首次入口和循环体回边](assets/12-loop-incoming.png)

把它写成SSA教学记法：

```text
entry:
    i0 = 0
    s0 = 0
    goto head

head:
    i1 = phi(entry: i0, body: i2)
    s1 = phi(entry: s0, body: s2)
    if i1 < n: goto body
    else: goto exit

body:
    s2 = s1 + i1
    i2 = i1 + 1
    goto head

exit:
    return s1
```

这里不是Python代码，而是有标签、跳转和phi的教学中间表示。对应的可运行解释器在文末。

![循环体产生i2和s2，回到循环头时由phi接成下一轮的i1和s1](assets/13-loop-ssa.png)

看起来出现了一个“先用后定义”：head的phi提到i2，可i2的代码明明在下面。

关键在来边。第一次从entry进入时，phi只选i0，不读尚未执行的i2。只有从body回来时，它才选i2；这时body刚刚计算完它。

代码文本的上下位置，不等于每次运行走过的先后路径。

## 8. “静态一次”不等于“运行时只执行一次”

这一点值得单独停下来。

SSA要求的是：**同一个名字，在程序的静态文本中只有一个定义点。** 不是说这条定义指令在整个运行期间只能执行一次。

循环每绕一圈，head里的同一条phi又执行一次，得到这一轮的值；body里的同一条加法也可能再次执行。指令位置只有一个，动态执行实例可以有很多。

![一个静态定义位置，可以在循环运行时出现多个动态执行实例](assets/14-static-dynamic.png)

对n=4，我们每次进入head时记录(i1, s1)：

- 从entry来：(0, 0)，继续循环。
- 从body来：(1, 0)，继续。
- 从body来：(2, 1)，继续。
- 从body来：(3, 3)，继续。
- 从body来：(4, 6)，退出。

![n等于4时五次进入循环头的实际解释器记录](assets/15-loop-trace.png)

如果把循环想成“同一个变量被改了很多次”，SSA似乎很矛盾。如果把它想成“同一张计算模板被执行很多次，每次按来路接好这一轮的值”，就顺畅多了。

## 9. 一个微妙陷阱：同一块里的phi要一起接值

假设循环每次只交换a和b。循环头的两条phi，可以在回边上分别取上一轮的b、上一轮的a。

从a=1、b=2出发，绕一圈后应该是a=2、b=1。

![交换用的两条phi必须从同一份进入前的值中取数](assets/16-parallel-phi.png)

若解释器偷懒，先把新a写成2，再读取已经改过的a来生成b，就会得到(2, 2)，把旧的1弄丢了。

因此，同一基本块开头的phi，应先根据前驱选择并读出所有输入，再一起交付结果。本文解释器用一个临时字典保存所选值，最后统一更新环境。

![先读完再提交得到正确交换，边写边读会覆盖还没使用的旧值](assets/17-swap-pitfall.png)

这不是要求CPU必须同时执行两条指令，而是要求实现保持这种并行赋值的语义。真正把SSA变回普通机器操作时，也得处理好类似的搬运次序。

## 10. phi该放哪？先找“原来必经，往前却未必”的边界

小程序可以靠眼睛在汇合处补phi。大程序若对每个变量、每个汇合点都补一份，可能塞进大量没有必要的节点。

再看left这个块。从left出去时，我们知道x1定义过了。但刚踏进join，这种“所有路径都经过left”的保证就消失了，因为另一路也能来到join。

join就在left的支配边界上。

![从left控制住的一条来边跨到join，另一条来路带来了不同定义](assets/18-dominance-frontier.png)

稍精确一点：Y属于X的支配边界，是指X支配Y的至少一个前驱，却不严格支配Y。严格支配就是支配但不等于自己。这个“严格”不是咬文嚼字；循环里，一个块可能出现在自己的支配边界上。

对累加循环，head支配body，但回边又进入head本身。head不会严格支配自己，所以循环头能够成为接值的位置。

![循环回边说明一个块为什么可能落在自己的支配边界上](assets/19-loop-frontier.png)

经典构造方法从变量的定义块出发，沿支配边界放置phi；新增phi本身又产生了一个定义，因此还可能需要继续处理它的边界。之后再按合适顺序重命名定义和使用。

这是理解1991论文的一条路线，不是本文已经完整实现了那篇论文的高效算法。本文的小图检查器直接按定义计算支配关系与边界，方便读者核对；它不追求生产编译器的构造速度。

也并非只要看到两个前驱就一定得为所有变量放phi。如果同一个定义已经覆盖两边，或者某个变量之后根本不用了，还可以少放或删除相应节点。SSA有不同构造与精简形式，不能把所有实现压成一条口诀。

## 11. 来处清楚了，优化能省下什么

把奖励例子改一下：左右两路都给7，最后再加2。

```text
left:  x1 = 7
right: x2 = 7
join:  x3 = phi(left: x1, right: x2)
       y1 = x3 + 2
```

虽然还不知道flag真假，但知道哪条来路都给7，就能确定x3=7，进而确定y1=9。

![两条来路都提供常量7，phi结果和后续加法可以传播成常量](assets/20-constant-propagation.png)

反过来，原来的两路分别是3和1，就不能在不知道条件时把x3随便认成某个常量。

这件事也能不用SSA分析。SSA的价值不是发明了“7+2=9”，而是把值的依赖关系整理得更直接：这次使用对应哪个定义、一个定义的结果又流向哪些地方，都更容易追踪。

![按值的使用关系传播已知常量，不必把不同定义继续混在同一个名字里](assets/21-sparse-notifications.png)

附带程序实现了一个很保守的常量传播：只有所有phi来值都已知且相等，才承认其结果为常量。它没有分析哪些边永远不会执行，所以不冒充完整的稀疏条件常量传播算法。

在“两路都7”的小例子中，替换常量前，实际走过的路径含一次加法；替换后是零次。两种flag输入的返回值都是9。这是教学解释器的运算计数，不是某台CPU的提速测试。编译速度、机器指令和最终耗时都不能从这个计数直接推出。

## 12. phi最后一定会变成一条机器指令吗

不一定。

可以先把奖励例子的phi想成：left到join之前，把左路结果交到一个统一出口；right到join之前，把右路结果交到同一个出口。每次实际只走一条边，因此不会同时交两份值。

![在进入汇合点的各条边上交付对应值，是理解消去phi的一种方式](assets/22-out-of-ssa.png)

实现中可能需要插入复制，也可能因为前后恰好分配到同一个寄存器而省掉复制。若边的两端还有别的分叉、汇合，放置复制的位置也要仔细处理，必要时会拆开边。

我们这里只解释去SSA的方向，不给出一个处理所有图与所有寄存器冲突的完整后端。刚才的交换陷阱提醒我们：搬值顺序同样属于正确性，不能一看到phi就机械地顺序写两个赋值。

还有一个重要边界：给指针名字加上编号，不会自动让它指向的内存只被写一次。两个不同名字仍可能指向同一地址。标量SSA把值的来处说清楚了，内存别名与读写依赖仍需额外分析。

![指针名字不同，所指的内存仍可能相同，标量SSA不能消除别名问题](assets/23-memory-boundary.png)

## 13. 看一眼真实的LLVM写法，再跑我们的小实验

LLVM的phi也把值与前驱成对排列。例如在固定的LLVM 18.1.8语法中：

```text
%x = phi i32 [ 3, %left ], [ 1, %right ]
%y = add i32 %x, 2
ret i32 %y
```

i32表示32位整数；百分号是LLVM局部值或块名字的记法。phi里也可以直接写常量，不一定先单独定义x1、x2。

[完整的原创LLVM IR示例](examples/bonus.ll)把前面的分支和标签也列齐。这份例子按官方语言规则核对，但本次环境没有实际运行LLVM编译器；不要把下面的教学解释器结果说成LLVM实测。

![教学phi记法与LLVM值前驱配对的对应关系](assets/24-llvm-pairs.png)

真正已经运行的是[SSA教学解释器](examples/ssa_lab.py)。它只用Python标准库，实现整数复制、加法、乘法、比较、分支、返回和phi；没有指针、溢出、异常、I/O或LLVM的poison语义。

可以这样运行一个完整例子：

```python
from ssa_lab import sum_loop, run
result = run(sum_loop(), {"n": 4}, trace=True)
print(result["value"])
for event in result["trace"]:
    if event["block"] == "head":
        print(event["phi_values"])
```

它返回6，并打印出前面五次进入循环头时的phi值。你可以改n=0：第一次进head就应直接退出，结果仍然定义良好，为0。

![本稿检查器抓住三类错误：重复定义、遗漏来边、定义未覆盖使用](assets/25-invalid-programs.png)

实际运行的检查包括：9826组分支输入同时验证原程序与常量替换版本；311个累加循环输入；1701组交换循环输入；2000个随机控制流图，把支配关系与“删去一个节点后还能不能到达”的独立方法对照。随机种子为199110。三个故意写错的程序分别触发重复定义、phi遗漏前驱、定义不支配使用的拒绝。

这些检查的范围和执行方法写在[实验说明](examples/README.md)。它们不是任意程序正确性的证明，也不是对真实LLVM优化器的全套测试。

最后，看一次n=4的执行动画。亮起的是当前进入的基本块；循环头同时显示这一轮真正选中的i1、s1。动画来自解释器的实际记录，不是随手排的一张循环示意。

![根据实际解释器轨迹依次点亮基本块的累加循环动画](assets/26-loop-execution.gif)

## 14. 给自己留一个小检查

如果把奖励程序的右路改成也给3，汇合处x3能确定为常量吗？若再把右路改成接收一个未知整数input呢？

第一种情况可以，x3恒为3；第二种情况通常不能，仅凭SSA写法并不知道input的值。名字干净，不等于信息凭空增加。

SSA真正做的事，是把一团“同名但不一定同源”的关系，整理成可以追问的结构：**这个值在哪里产生？使用时，那次定义一定发生了吗？如果来自不同路径，汇合处到底接了哪一份？**

这些问题答清楚，优化器才能更放心地删、搬、合并计算。而循环依然能转，分支依然能选；改变的是程序在编译器眼里的组织方式。
