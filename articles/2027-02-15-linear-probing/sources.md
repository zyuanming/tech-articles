# 来源与说明

## 图片

12 张正文图与 `cover.png` 全部是本文原创的教学示意，由 `examples/build_figures.py` 生成。几何断言写在 `examples/figkit.py` 里：文字不出画布、不互相压、任何字号的文字换算到 354 px 宽的显示宽度后不小于 12 px。没有使用任何照片、截图或第三方素材，因此不涉及第三方署名与许可。

这意味着两件事：图里没有一张是真实库的内部状态快照；第 10 张（SwissTable 分组控制字）里的 16 个控制字节是我为了说明机制手写的一组示意值，除两个指纹恰好相等之外都是随手写的十六进制，没有一个字节是从 Abseil 或 hashbrown 的运行时 dump 出来的。

## 数字

正文和图片里的每个数字都由 `examples/probe.py` 算出、`examples/run_model.py` 写进 `examples/results.json`，`examples/build_figures.py` 只从 `results.json` 取值。跑一遍：

```sh
cd examples && python3 run_model.py && python3 build_figures.py
```

纯标准库（画图需要 Pillow），`run_model.py` 约 47 秒，其中一半花在 65 537 个槽那张表上（装载到 98%，插入时探测链很长）。

模型设定：

- **哈希**：splitmix64，种子固定。键是 64 位无符号整数，生成时排掉重复。没有用 Python 内置 `hash`——它的值是随进程随机化的，实验不可复现。
- **表长**：取素数 4099 / 65 537 / 131 101 和 64（格子图）、11（Robin Hood 手算）。素数表用 `k % m` 当起点，这样不需要额外混洗；如果用 2 的幂当表长，`k & (m−1)` 只用到低位，需要先混洗。
- **探测次数**：一次探测 = 检查一个槽（比较它是不是空、是不是墓碑、是不是要的键）。插入记的是「从起点到落点」的槽数；查找记的是「从起点到命中或到空槽」的槽数。
- **成功/失败**：成功查找查的是表里已有的每一个键（α = 0.9 那张表是 3689 个），取算术平均；失败查找查 1500 个（大表那张 2000 个）从未插入的键。
- **Robin Hood**：槽里存 `(键, 起点)`，插入时如果占位者的探测距离小于来者的距离就交换，被换出来的那个带着自己的起点继续往后。实测里「交换次数」统计的是这种让位发生的次数。
- **双散列**：步长 `1 + (k // m) % (m−1)`，m 取素数，保证步长与表长互素、探测序列能走遍全表。
- **重建对照**：删掉 1200 个键之后，把剩下 2284 个键按原顺序插进一张新表，再用量同一批不存在的键。
- **公式**：`½(1+1/(1−α))` 与 `½(1+1/(1−α)²)` 是线性探测的成功/失败期望探测次数；链地址的成功是 `1+α/2`、失败是 `α`；双散列成功按 `−ln(1−α)/α`（教科书给的近似）列出。这些式子用来对照，不参与任何测量。

关键数字的来历：

- **5.55 / 55.71 / 355**：m = 4099、3689 个键（α = 0.90）时，成功查找的平均与最长探测次数、失败查找的平均探测次数。
- **2.25 / 6.625**：α = 5/7 时两个公式的值，正文里手算过一遍：`½(1+1/(2/7))` 与 `½(1+1/(2/7)²)`。
- **7 格 / 25 格**：m = 64 的格子图在 32 键、57 键时的最长簇长度。
- **407 / 1167 / 1925**：α = 0.90、0.95、0.97 时最长簇的格数（m = 4099）。
- **2026 / 355**：α = 0.90 时，3689 个键里一次命中的键数，以及最坏那个键的探测次数。
- **2.53 / 49**：同一装载率下双散列的平均与最长探测次数。
- **575 / 1249.9**：α = 0.98、m = 4099 时失败查找的实测与公式值。
- **966.4 / 1250.0 / 6897**：换成 m = 65 537 重做 α = 0.98：实测失败探测、公式值、最长簇格数。
- **355 / 30 / 4.63**：m = 65 537、α = 0.88 时线性探测与 Robin Hood 的最长探测次数，以及两者相同的平均探测次数。
- **110052**：同一张表上 Robin Hood 让位发生的次数。
- **22.7 / 3.0 / 3.79 / 5.15 / 1.57**：m = 4099 删除实验的三个平均值。22.7 是删除前后两次（三次实验分别是 22.7、25.4、17.9，正文引第一次），3.0 是重建后；3.79、5.15、1.57 是成功查找在删除前、删除后、重建后的平均值。
- **6 步**：手算表里查键 22（起点 1，不在表里）要检查的槽数。

## 明确没有做的事

- **没有测任何真实库的吞吐或延迟。** 全文没有 benchmark，没有 C/C++/Rust 代码，也没有 `perf`。我的模型是一次 Python 解释器里的 `list` 索引，「探测次数」与真实实现可比（同样的算法、同样的装载率），「耗时」不可比。正文没有给任何微秒数。
- **没有测缓存行为。** 正文说线性探测的几个候选槽落在同一条 64 字节缓存行——这是布局的事实，不是我量出来的命中率。双散列「缓存不友好」的说法同理，来自访存模式，没有实测。
- **没有读 Peterson 1957 的原文。** 1957 年那篇《Addressing for Random-Access Storage》是我按二手叙述引用的：它在开放寻址的早期分析里算了包括「挨着往后试」在内的几种探测顺序，并注意到成片连续占用带来的代价。我没有核对他的具体表格与符号。
- **没有读 Knuth 1963 那份笔记。** 公式的归属按《计算机程序设计艺术》第三卷 6.4 节的通行说法写，那一节的正文与习题里给出了这两个式子；1963 年笔记本身没有看到。
- **Robin Hood 1985 的原文只到摘要层面。** 正文引的结论——不改变成功查找的平均探测次数、把波动压小——与我的实测一致（平均 4.63 对 4.63，最长 355 对 30），但我没有核对论文里的界与证明。
- **没有核对 Go / Rust / Python 的实现细节。** 第 11 张图里四种实现的冲突处理方式来自各自的发布说明与文档（见下），没有读这些库的源码，也没有跑它们做对照。
- **没有测 HashDoS。** 正文只用一句话提到 2011 年那次演示，没有复现，也没有构造恶意键。
- **没有目视检查图片。** 见 `review.md`。

## 模型与真实实现的差别

三处值得记住：

1. **一次探测不等于一次内存访问。** 在真实机器上，落在同一个缓存行里的连续槽可能只要一次加载；跨行了就是一次未命中。我的模型里每一步都是同样的代价，所以双散列在「比较次数」上赢，在「内存访问」上不一定。
2. **哈希函数比我的更慢也更均匀。** 真实实现常用带密钥的哈希（Rust 默认 SipHash-1-3），一次哈希几十纳秒，比我这个 splitmix64 贵得多；换来的是攻击者猜不到键的落点。正文没有把哈希开销算进任何数字。
3. **扩容策略会影响曲线。** 我的实验都是「一次装到指定装载率再测」，真实库是倍增式扩容、边插边重排，所以真实系统的平均装载率通常停在扩容阈值（0.7 上下）附近，而不是 0.9。

## 引用与延伸

- W. W. Peterson, *Addressing for Random-Access Storage*, IBM Journal of Research and Development 1(2), 1957, 130–146. DOI: 10.1147/rd.12.0130。开放寻址早期分析的起点，「连续占用区」的观察出处。
- D. E. Knuth, *The Art of Computer Programming, Vol. 3: Sorting and Searching*, Addison-Wesley, 1973, §6.4（Hashing）。线性探测的成功/失败期望探测次数、墓碑删除与回移删除都在这一节。
- P. Celis, P.-Å. Larson, J. I. Munro, *Robin Hood Hashing*, 26th Annual Symposium on Foundations of Computer Science (FOCS), 1985, 281–288. DOI: 10.1109/sfcs.1985.48。
- Abseil, *Swiss Tables Design Notes*，https://abseil.io/about/design/swisstables ；以及 *Swiss Tables and absl::Hash*，Abseil 博客，2018-09-27。7 位 H2 指纹、16 个一组的控制字节、用 SSE 一次比较 16 个候选、墓碑不终止探测而空槽终止探测，都出自这两份文档与 `raw_hash_set.h` 的头注释。
- Go 1.24 Release Notes，https://go.dev/doc/go1.24 。「内置 map 换成基于 Swiss Tables 的实现，可用 `GOEXPERIMENT=noswissmap` 关闭」。
- Rust 1.36 发布公告，2019-07-04，https://blog.rust-lang.org/2019/07/04/Rust-1.36.0/ 。`HashMap` 换成 `hashbrown`（SwissTable 的 Rust 实现），默认哈希仍是 SipHash-1-3。
- PEP 456, *Secure and interchangeable hash algorithm*（Python 3.3 起默认对字符串哈希加随机化种子）。
- A. Klink, J. Wälde, *Efficient Denial of Service Attacks on Web Application Platforms*, 28C3, 2011。哈希碰撞攻击的公开演示。
