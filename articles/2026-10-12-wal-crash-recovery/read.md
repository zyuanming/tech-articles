# 已经显示“保存成功”，断电后还算数吗？WAL把承诺写在修改前面

你在做一个小游戏。仓库A里有100颗宝石，仓库B里有40颗。玩家点击“转移30颗”，程序先把A改成70，再把B改成70。

界面看起来只发生了一件事。存储设备却可能先完成第一处写入，第二处还没落稳，机器就断电了。

重新打开游戏：A是70，B仍是40。30颗宝石没有被偷走，只是程序把“一件事”拆成了两个不同时间完成的动作。

更让人不舒服的是另一种情况：刚才明明看见“保存成功”，重启后又变回100和40。系统究竟什么时候才有资格说成功？

![两页记录的半次转移](assets/01-half-transfer.png)

这篇从两个数字的小账本出发，理解预写日志，英文是Write-Ahead Logging，通常缩写成WAL。我们会真的在模型的不同步骤插入崩溃，看看哪些顺序能恢复，哪些顺序会丢掉必要证据。

## 1. “程序改了”，至少可能指三件事

第一件：程序在内存里改了数字。内存很快，但本篇假定断电后这些工作状态全部消失。

第二件：程序请求把数据写到持久存储。请求发出，不一定等于设备已经保证它能跨过本篇讨论的故障。

第三件：相应内容已经持久化。下文说“落稳”，专门指第三件，不把一次普通写入函数返回直接当作这个保证。

为了画图，我们把保存A、B的地方叫作两张“数据页”。真实数据库的页能装许多记录，这里每页只装一个数。内存里的副本改过而持久副本尚未跟上时，常被称作脏页；“脏”只是版本不一致，不是数据一定错了。

![内存副本与持久副本](assets/02-two-layers.png)

一个交易性的保存操作，至少想给出两个承诺：

- 原子性：转移作为一个整体生效，不留下只扣不加的半成品。
- 持久性：已经对外确认成功的转移，不能因为本模型中的一次崩溃就消失。

这两句不是“每时每刻磁盘上都只能有完整结果”。磁盘上暂时出现过渡状态，可以接受；前提是系统保留足够证据，重启后能恢复，并且不能把未恢复完的状态交给玩家使用。

![原子性与持久性分别保护什么](assets/03-two-promises.png)

## 2. Jim Gray关心的，是故障前后同一个承诺

1981年，Jim Gray的《The Transaction Concept: Virtues and Limitations》把事务、日志和恢复放在同一条论述线上。原文讨论的不只是“执行一个动作”，还包括撤销它、在故障后重做它，以及哪些更大的现实动作超出了事务模型的范围。[原论文](https://www.cs.utexas.edu/~dahlin/Classes/GradOS/papers/Gray81.pdf)

![Jim Gray在Tenacious船上，2006年1月，Tony Hey摄影](assets/04-jim-gray-tenacious-original.jpg)

这张照片由Tony Hey拍摄，摄于2006年1月，出自微软研究院出版的《The Fourth Paradigm》第234页。这里采用原书中嵌入的完整JPEG，没有裁切或重绘；按CC BY-SA 3.0 US使用，具体署名、来源和许可见文末素材说明。

不要把这段历史读成“某个人在某一天发明了所有WAL”。本文只把1981年的论文当作一个可核查的历史窗口：很早以前，系统研究者就已经认真区分，发生过、应该保留、需要撤销，究竟是不是同一回事。

今天我们仍能在PostgreSQL 18的官方说明中看到WAL的核心顺序：描述修改的日志先持久化，相应数据页的修改才可以写回持久存储。[官方说明](https://www.postgresql.org/docs/18/wal-intro.html)

## 3. 先造一间很小的实验室

真正数据库还要处理并发、锁、半张页写坏、磁盘故障、日志校验、备份和恢复时再次崩溃。一下全装进来，会看不清最基本的依赖关系。

本篇先约定：

1. 只有A、B两页。初始持久状态是100、40。
2. 事务串行运行，同一时刻最多一笔；上一笔提交记录落稳后，下一笔才能开始。
3. 一次数据页持久写入是完整的；日志落稳后总是一个完整前缀，不会中间缺一条。真实设备如何提供或补强这些保证，这里不实现。
4. 崩溃会清空内存和未落稳的日志尾部，但不损坏已经持久化的内容。
5. 保留从已知一致起点开始的全部日志；不做日志截断，也不实现运行中的主动回滚API。
6. 恢复结束前，不开放玩家读写。

![模型故障边界](assets/05-model-boundaries.png)

这是一个允许“未提交的数据页先写回”，也允许“提交时不立刻写回全部数据页”的小模型。它故意保留两种麻烦，让我们同时看见撤销和重做的用途。后面给它们补英文名。

程序是原创教学模拟器，不打开数据库、不调用真实磁盘同步，也不会真的让你的机器断电。

## 4. 在旁边另开一本顺序账

设第一笔事务叫T1，目标是把30颗宝石从A转到B。除了改内存，我们还生成这些日志记录：

- 第1条：T1把A从100改成70。
- 第2条：T1把B从40改成70。
- 第3条：T1提交。

每条修改记录都保存事务编号、对象、修改前的值和修改后的值。“提交”是单独的记录，不靠“最后看见两个数都改了”来猜。

![第一笔事务的三条日志](assets/06-three-records.png)

这里的记录序号是顺序账的位置，帮助我们说清楚“至少落稳到第几条”。它不是时间戳。真实系统常使用日志序列号LSN，具体编码和用途比本例丰富。

修改前的值让系统能撤销未完成事务；修改后的值让系统能补上需要保留的效果。这是本模型选择的日志格式，不是说所有WAL产品都必须逐字段保存这一对值。

“预写”的先，关键在于持久顺序：**不能让修改后的数据页先落稳，却把解释这次修改所需的日志留在易失内存里。** 日志进入内存缓冲区，还没满足这条规则。

## 5. 两道门：写页之前，承诺之前

第一道门，管数据页：要把A的新值70写回持久存储，至少先让第1条日志落稳。要写回B的新值70，至少先让第2条落稳。

![日志先于相应数据页](assets/07-page-before-gate.png)

第二道门，管对外承诺：只有T1的提交记录也落稳了，系统才能按本文的持久性承诺回复“成功”。

因为日志是完整前缀，第3条落稳也意味着前面两条修改记录已经落稳。不是只把孤零零的“提交”两个字保存下来。

![成功答复要等待提交记录落稳](assets/08-ack-after-commit.png)

你可能问：既然都要等待，为什么不干脆把两张数据页都写好再回复？

当然可以采用更严格的策略。WAL给了另一种选择：先持久化紧挨着的一段日志，就能把分散数据页的写回留给后续。收益来自写入组织和等待方式的改变，不是凭空取消持久化成本。真实系统还可能让一次日志同步覆盖多笔事务；本文没有测吞吐量，也没有给出“快几倍”的数字。

## 6. 已提交，页却没写全：需要重做

现在假定第1、2、3条日志都已落稳，数据页仍是100、40，然后崩溃。

只看数据文件，会误以为T1没有发生。但持久日志明确留下了提交决定。恢复时按记录把A写成70，把B写成70，就能兑现这笔事务。

这个补做叫重做，英文REDO。

![已提交但数据页落后](assets/09-redo-needed.png)

注意，是恢复已记录的效果，不是重新向玩家收一次操作。日志里的“把A设为70”和业务层再做一次“A减30”不一样；后者如果执行两次，A可能变成40。

这也解释了为什么数据库恢复与网络请求去重不是同一个问题。WAL能帮数据库保存提交结果，却不会自动阻止客户端因超时而再发送一笔新的转移请求。

## 7. 未提交，页却已写了一半：需要撤销

换一个崩溃点：第1条日志已落稳，A的数据页也已经写成70，但T1尚无持久提交记录。B仍是40。

这时不能说“扣款都在磁盘了，就算转移成功”。本模型的决定依据是持久提交记录。T1尚未提交，应把A恢复为日志里的旧值100。

这个回退叫撤销，英文UNDO。

![未提交事务的页已经写回](assets/10-undo-needed.png)

如果没有先保存第1条日志，崩溃后我们只看见A=70，未必知道原来是100，也无法判断这70是哪一笔事务的效果。数据页比日志抢先落稳，就可能把恢复所需的证据弄丢。

第一道门保护的正是这个危险时刻。

## 8. 一个更像现场的例子：两个事务混在持久页上

继续沿用T1。它已经提交，把逻辑结果变成70、70，但B的新页可以暂时还没写回。

随后T2想反向转10颗：A从70到80，B从70到60。于是追加：

- 第4条：T2把A从70改成80。
- 第5条：T2把B从70改成60。

让日志落稳到第5条，A页写回80，B页还留着最初的40。此刻崩溃。

![两笔事务的日志和混合数据页](assets/11-mixed-crash.png)

持久状态是A=80、B=40。它既不是最初的100、40，也不是T1完成后的70、70，更不是T2完成后的80、60。

不过证据没有丢：T1有提交记录，T2没有。目标应该是保留T1，撤去T2，最后得到70、70。

这里采用一个容易检查的恢复过程：先顺序重做日志里所有修改，再逆序撤销没有持久提交记录的事务。先让记录里的历史走到尾部，再消掉未完成尾巴。

![先重做全部记录，再逆序撤销未提交尾部](assets/12-two-passes.png)

先重做，第1、2、4、5条依次让页状态变成：

70、40 → 70、70 → 80、70 → 80、60。

接着逆序撤销T2：第5条把B还原成70，第4条把A还原成70。

![撤销两步之后回到70和70](assets/13-reverse-undo.png)

中间短暂出现80、70并不代表一次新的业务提交。整个恢复过程尚未开放给玩家；只有最终状态才用于继续服务。

## 9. 为什么撤销要倒着走？

拿一个更小的反例：同一笔未提交事务先把A从100改成70，又把A从70改成60。

撤销时，先撤第二次，60回到70；再撤第一次，70回到100。

如果照正序写旧值：先写100，再写70，最后反而停在中间状态。

![同一页改两次时的撤销顺序](assets/14-undo-order.png)

不是因为“凡是恢复都应该倒着来”。重做仍按原来的先后顺序；撤销是沿着依赖关系退回去。鞋先穿、袜后穿很别扭，脱衣动作的逆序直觉在这里也有一个严格的数值版本。

## 10. 十几行代码，先看见完整逻辑

下面的函数只接受第3节约定的模型：串行事务、完整保留日志、完整的持久前缀、页级原子写入，以及恢复期间无其他访问。它不是通用数据库恢复器，也不校验任意外来日志。

记录U表示修改，依次保存类型、事务号、页名、旧值、新值；C表示提交。

```python
def recover(disk, durable_log):
    """只用于正文的串行、全日志模型。"""
    result = dict(disk)
    winners = {r[1] for r in durable_log if r[0] == 'C'}
    # 顺序重做所有保留的修改
    for r in durable_log:
        if r[0] == 'U':
            result[r[2]] = r[4]
    # 逆序撤销没有持久提交的尾部
    for r in reversed(durable_log):
        if r[0] == 'U' and r[1] not in winners:
            result[r[2]] = r[3]
    return result
```

![恢复代码的输入输出边界](assets/15-code-contract.png)

`winners`这个名字只是恢复文献中常见的简写思路：在本函数里，它精确表示“持久日志中存在提交记录的事务编号集合”。它与玩家输赢没有关系。

代码从当前持久页开始，顺序写入所有记录的新值，再倒序写回未提交事务的旧值。主例返回`{'A': 70, 'B': 70}`。

一般理由也可以不靠代码看懂：对于日志中改过的每个对象，顺序重做后，它处在最后一条相关记录的新值上；由于事务串行，未提交事务只可能出现在末尾。把这个尾部的修改逆序退回，就回到了最近一次持久提交之后。日志从未涉及的对象，其页值不应被恢复过程改动。

这段理由依赖模型边界。如果允许多个事务交错、允许某笔事务结束后又用不同规则回滚，不能把同一小函数原封不动搬过去。

## 11. 恢复的时候，又断电呢？

在主例的重做、撤销中间，再挑一个位置崩溃。只要完整日志还在，重启后仍然从头执行同一恢复过程，就能再次走到70、70。

这里有两个支撑条件。第一，恢复期间没有新的业务写入混进来。第二，日志没有被过早删除。

![恢复中断后从保留的日志重新开始](assets/16-recovery-again.png)

我们使用“设为某值”，重复写70仍是70，这叫幂等的赋值。它与“每执行一次就减30”的操作不同。

不过，单条赋值幂等，并不自动证明任意排序都安全。整个算法还要遵守重做正序、撤销逆序，以及前面列出的输入约束。这里的重复恢复成立，是这些条件共同作用的结果。

![赋值与重复扣减的区别](assets/17-assignment-not-decrement.png)

实际数据库希望避免每次重启都完整重跑很长历史，还要允许更复杂的并发和回滚。它们会保留更多进度信息。我们的简洁来自有意缩小问题，不是从真实系统里发现了一个被忽略的万能捷径。

## 12. 把两个开关命名，复杂度就有了来处

第3节故意放开的两个策略，现在可以命名了。

Steal：一笔事务尚未提交，它改过的数据页也允许写回持久存储。可以理解为缓冲区管理者提前收回这块内存的使用权；不是“偷走玩家的数据”。这种自由带来撤销未提交效果的责任。

No-force：事务提交时，不强制它改过的全部数据页立即落稳。这种自由带来崩溃后补做已提交效果的责任。

![缓冲策略的两个独立开关](assets/18-policy-grid.png)

本篇选择steal加no-force，所以同时需要讨论UNDO和REDO。若改变开关，所需恢复工作也会改变；不要把这个小模型的“每条日志都存旧值和新值”当成所有数据库的统一规定。

1992年，C. Mohan、Don Haderle、Bruce Lindsay、Hamid Pirahesh和Peter Schwarz发表ARIES论文。论文处理细粒度锁、部分回滚等更复杂场景，并把重演历史、页上的日志序列信息，以及对回滚本身的记录结合起来。[原论文](https://www.cs.cmu.edu/~15849g/readings/mohan92.pdf)

![从本文小模型走向ARIES的额外责任](assets/19-aries-boundary.png)

本文代码借用“先重做历史，再撤销未完成部分”的教学顺序，但没有实现ARIES的分析阶段、脏页表、页LSN判断、补偿日志记录或并发恢复，不能称为ARIES实现。

同样，SQLite官方文档里的WAL模式，是把新的页内容追加到单独WAL文件，再通过检查点推进数据库文件；它有自己的读取、提交和检查点规则。不能拿本文“未提交页提前覆盖数据文件”的假设，去描述SQLite这个模式的具体实现。[SQLite说明](https://www.sqlite.org/wal.html)

## 13. 我们实际把哪些地方弄“崩溃”了？

配套的[可运行实验](examples/wal_lab.py)不是给一条理想时间线拍照。它枚举状态：程序发出到第几条记录、日志落稳到哪一条、A和B各自持久化到哪个版本。

从一个状态出发，只走合法动作：发出下一条记录、让日志前缀前进一步，或者在日志已覆盖相关修改时写回数据页。到达一个从没见过的状态，就把它加入待检查集合。

![枚举合法状态而不是乱拼日志与页](assets/20-reachable-state-search.png)

对固定的两笔事务，实际找到79个可达状态、156条状态转移。每个状态都当作一次可能的崩溃现场：把未落稳尾部丢掉，再恢复。另在恢复过程每一次实际页赋值之后插入崩溃，一共检查292个这样的中断位置。

正确答案由另一种计算方式给出：维护每笔事务的私有修改集合，只有读到持久提交记录时，才一次性把这笔集合发布到参考状态。这个检查器不从混乱的数据页上猜提交结果。

随后把初始A、B，以及两次转移的数量，分别遍历−2到2的整数，共625组程序、49375个可达状态。负数只是检查恢复算术的输入，不表示游戏应该允许负库存。业务约束与恢复机制，是不同层的责任。

![实际测试范围和两个故意破坏的顺序](assets/21-test-scope.png)

这些检查都实际通过；也实际验证了两个反例：允许数据页跑到日志前面，会丢失撤销证据；在提交记录落稳前确认成功，会让被承诺的结果在崩溃后消失。有限枚举帮助找错，并不代替前面的条件和理由，更不是硬件可靠性认证。

## 14. 没收到成功，不等于一定失败

再看一个容易误判的时刻：提交记录已经落稳，系统正准备给玩家发回复，连接断了。

从存储恢复的角度，这笔事务已经提交。从玩家的角度，却可能完全没看见“成功”。

![持久提交与客户端看到答复之间有空隙](assets/22-commit-before-reply.png)

因此，客户端没有收到回复，只能说明结果暂时不确定，不能直接断言“数据库一定没做”。重新发起业务请求之前，往往需要请求编号、查询结果或去重设计。那是建立在事务之上的另一层协议，本文不把它偷偷塞进WAL三个字里。

日志也不是永久备份的替身。若数据页和日志所在设备一起损坏，本文“持久内容仍在”的前提已经不成立。检查点可以缩短恢复历史，但必须先建立足够可靠的一致起点，并确认旧日志不再被恢复、读者或备份需要；不能因为文件看起来很大就手动删掉WAL。

![本篇恢复能解决与不能解决的边界](assets/23-boundaries.png)

最后留两道能自己算的题：

第一题，仍用第8节主例，但在崩溃前把T2的第6条提交记录也落稳，数据页仍是80、40。恢复结果是什么？

第二题，保留主例到第5条的日志，恢复执行到“B设为60”后再次崩溃，日志不变。重新恢复，会不会把10颗又转一次？

第一题应是80、60，因为两笔事务都有持久提交记录。第二题仍是70、70，因为T2没有提交，重复恢复最后仍会撤销它。

![主例六个恢复赋值步骤的动画](assets/24-recovery-animation.gif)

WAL最值得记住的，不是“多写一个文件就安全”。它把一句对外承诺，拆成了可检查的先后关系：数据页不能抢在必要证据前面；成功答复不能抢在持久提交前面。

当故障真的发生时，恢复程序不是猜“最后看起来做到了哪一步”，而是从留下的证据中分清，哪些效果必须保留，哪些效果必须撤去。
