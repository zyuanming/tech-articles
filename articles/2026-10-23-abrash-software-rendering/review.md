## 查证线

- **历史部分按署名文章写**：Michael Abrash 在《Quake's Lighting Model: Surface Caching》里讨论静态世界表面的照明与绘制，他把关键设计思路归于 John Carmack。文章明确这是合作开发的技术记录，不改写成「一个人写出整个引擎」，也没有把这套安排推广成所有 Quake 版本或现代 GPU 的统一做法。
- **源码对应点到函数**：`D_CacheSurface` 检查当前纹理、照明调整值与动态光状态，`D_SCAlloc` 使用 rover 与块管理。文章据此说明「读源码要看条件，而不只认函数名」，同时点明 rover 分配器不是本文的教学 LRU。
- **主例全部自造且可手算**：`32×16` 灰度表面，`4×4` 周期花纹，`2×2` 小块取 `80` 或 `200`，`9×5` 亮度节点。左上格四角亮度 40、57、71、88，权重 `3/8、1/8、3/8、1/8`，得 `L=40×3/8+57×1/8+71×3/8+88×1/8=59.75`，取整到 `59`；再算 `S=floor(200×59/255)=46`。取整位置单独交代，便于重写代码复现同一张图。
- **面积账分开记**：四级 mip 为 `32×16`、`16×8`、`8×4`、`4×2`，各需 `512`、`128`、`32`、`8` 字节，同时存齐 `680` 字节，比只留第 0 级多 `168` 字节。文章明确 capacity 是「每个灰度打包成一字节」的有效载荷预算，不是 Python 进程内存，也不含索引、对象与对齐开销。
- **失效条件是三件事**：输入是否相同、旧结果是否含已消失的动态项、内存里是否还留着。第六次请求动态项消失仍必须重建，因为缓存里那份是「有动态项的亮图」；示例把「可能少命中」和「返回错误图」当成不同取舍。
- **实验读数给全**：两份容量下 ABC 循环四遍重建 `12` 次，三份容量只建 `3` 次；`1024` 字节容量与重复请求串得到 `hits=9`、`builds=3`、`built_texels=1536`。费用模型以 `B=512`、`R=64` 个假设工作单位计算，`N=12` 时两式分别为 `6912` 与 `1280`，并明说这些单位不是周期或毫秒。
- **许可边界写在正文**：id 官方 README 把引擎代码许可与游戏数据分开，所以文章不拿游戏纹理、关卡或截图上桌；所有灰度图都来自自写程序。
- **配图身份**：十六张图是原创示意与程序输出数组的可视化，图注区分「数组裁剪」与「引擎摄像机画面」。
