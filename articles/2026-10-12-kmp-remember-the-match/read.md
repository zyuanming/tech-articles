# 已经看过的字，为什么还要重看？KMP 把失败变成下一步的线索

你在一条很长的日志里找一个词。

程序从左往右一格一格地比：第一个字相同，第二个相同，第三个也相同。眼看就要成功，下一个字却对不上。

接下来怎么办？

最省事的做法，是把起点往右挪一格，从目标词的第一个字重新开始。可刚才那些已经确认过的相同，真的一点用都没有吗？

![在文本中寻找连续出现的模式，标出从0开始的下标](assets/01-search-contract.png)

下面用一个小例子贯穿全文：在 ABABABACABA 里找 ABABACA。前者叫**文本**，后者叫**模式**，也就是要找的那串字符。这里找的是连续子串，中间不能跳字。

先别小看这个问题。文本很长、模式也不短的时候，一次失败就可能让程序从下一个起点从头再比一遍；如果每个起点都要重新确认一遍已经确认过的字符，浪费会随着文本长度一起放大。我们真正想要的，是既不漏掉答案，又别把力气花在已经知道的事情上。

把第一格编号为0，答案从第2格开始，你很快能用眼睛确认。难的是另一件事：程序怎样在不漏掉任何位置的前提下，少做重复劳动？

这正是 KMP 字符串匹配算法要解决的问题。它不要求你先背下那张“next 数组”；我们从一次失败里，把还能保留下来的信息一点一点捡起来。

## 1. 最朴素的搜索，浪费在哪里？

先看一个极端例子：模式是 AAAAB，文本是一长串全是 A 的字符。

每换一个起点，程序都要连着确认四次“A 等于 A”，到第五个位置才发现：“这里还是 A，不是 B。”然后从下一个起点，把同样的四个 A 再确认一遍。刚才那四个 A 其实是白看的——它们和上一个起点看到的是同一批字符，程序却当作全新信息，重新核对一次。

![重复字符让朴素搜索在多个起点反复确认同样的A](assets/02-repeated-work.png)

如果文本有40个A，模式长5，就有36个起点放得下整个模式。朴素实现每试一个起点做5次比较，一共180次。

一个答案都没找到，却做了大量重复确认。文本越长，这种“每个起点都从头比一遍”的浪费越明显；最坏情况下，比较次数会随文本长度和模式长度一起膨胀。

朴素方法并非一无是处——模式短、很快就失配的数据，它往往跑得不错，实际用起来也不慢。我们真正在意的，是能不能给最坏情况也找一个可靠的上限：不管数据长成什么样，比较次数都别失控。

## 2. 一次失败，实际上带着一张证据单

回到 ABABABACABA 与 ABABACA。

从文本第0格开始，前五个字符 ABABA 全部匹配。轮到文本第5格，文本是 B，模式期待的却是 C。

![前五个字符匹配，在文本下标5处B与模式C失配](assets/03-first-mismatch.png)

这次失败并不代表一无所知。

恰恰相反，它带回了一整张“证据单”。我们其实已经知道，刚走过的五个文本字符就是 ABABA——它是刚才逐格比出来、并且已经存进状态的结果，不用再猜。也不必再读一遍文件，更不必一个个去问它们是什么。后面所有的技巧，都围绕一件事：怎么把这张证据单用起来。

![已经匹配的ABABA可以由模式的前五个字符重建](assets/04-known-information.png)

给当前状态起两个短名字：

- i：这次准备比较的文本位置；
- j：已经连续匹配上模式开头的多少个字符。

此刻 i=5，j=5。因为下标从0起，下一个要比的是模式第5格，也就是 C。

注意 j 首先是个**长度**。只因为从0编号，它同时又等于“模式里下一个待比字符的下标”。这两个身份重合，后面的代码才写得简洁。

## 3. 哪一截旧结果，可以当作新开头？

把 ABABA 写在一张纸条上。

它的开头是 ABA，结尾也是 ABA。于是把模式向右挪两格时，旧匹配末尾那截 ABA，正好接住模式新开头的 ABA。

![ABABA的最长相同真前缀与后缀是ABA，长度3](assets/05-border.png)

这里要三个词，但它们都很普通。

**前缀**是从开头截下的一段。ABABA 的前缀可以是 A、AB、ABA。

**后缀**是贴着结尾截下的一段，比如 A、BA、ABA。

**真前缀**不把整串都拿走。我们正要找一个右移之后的新起点；要是允许“整段 ABABA 和自己相同”，那就等于一步没动，白折腾。

既是前缀又是后缀的同一串字符，有时叫 border，中文可以理解成“首尾相同的边”。它未必只有一个：ABABA 还能保留一个 A，只是长度3的 ABA 更长，留住的字符更多。

为什么优先挑最长的？因为它对应最小的、仍有希望的右移——模式挪得越少，越不容易跳过还可能命中的起点。留短了会多做无用功，留长了又会漏掉答案，最长的那个恰好卡在中间。先查最近的候选起点，才不会一下越过可能的答案。

## 4. 为什么跳过第1格，不会漏掉结果？

从起点0直接跳到起点2，听起来像条危险的捷径。

第1格怎么了？

我们已经知道文本第1格是 B，而模式第一个字符是 A。两者不同，第1格不可能是答案的开头。

![右移一格会让A碰到已知的B，右移两格才能保留ABA](assets/06-safe-shift.png)

换成一般说法：要保留旧匹配末尾的一段，这段文本就必须等于模式的新开头；而旧文本又等于刚匹配过的模式前缀，于是问题变成“模式自身的前缀和后缀能不能对上”。

**移动距离不是靠猜出来的，而是被已经知道的相等关系约束出来的。**

这句话值得记牢，后面建表和搜索都靠它：能跳多远，是算出来的，不是试出来的。

这个例子里，原先匹配5个字符，现在保留3个，起点向右移动 5−3=2 格。

## 5. 回退的是模式状态，文本这一格先别走

接下来这一步最容易写错。

把 j 从5改成3以后，文本第5格那个 B 还没被新的对齐解释。不能马上把 i 加一。

这里有个很自然的冲动：既然模式挪了，就顺手把文本指针也往右推一格，接着比下一个字符。真这么做，刚刚才对齐上的那个起点就被跳过，答案也跟着丢了。

我们仍旧拿同一个 B，去比模式第3格。这次模式第3格也是 B。

![文本指针停在同一个B，模式从期待C改为期待B](assets/07-same-character.png)

于是 j 从3涨到4，然后才去读下一个文本字符。

再往后，文本的 A、C、A 陆续匹配。到文本第8格，完整的7字符模式终于出现。结束位置是8，长度是7，起点就是 8−7+1=2。

![保持已知前缀后继续匹配，最终在起点2找到完整模式](assets/08-found-match.png)

你可以用手指在图上走一遍：文本的手指只往右走，模式的状态却会后退。一次失配，可能让同一个文本字符被比较不止一次；“文本不回头”和“每个字符只比较一次”是两码事。

为什么要死守“文本不回头”？因为在流式场景里，回头看是做不到的。数据从网络或文件一块块流过来，读过的部分可能已经不在手边，甚至根本不允许你回退缓冲。KMP 把“需要回头看的记忆”全部搬进了模式自己的那张表里——表只跟模式有关，与文本多长无关，所以文本可以一直往前流。

## 6. 先给模式做一份简短的备忘录

搜索时如果每次失败都重新找最长相同前后缀，省下来的工作又会被花回去。

所以，先只研究模式自己。

对模式的每个结尾位置 r，记下“到这里为止的这一段，最长相同真前缀与后缀有多长”，写成 pi[r]。pi 只是这张表的名字，跟圆周率没关系。

![ABABACA的前缀函数表为0、0、1、2、3、0、1](assets/09-prefix-table.png)

一个个看：

- A：没有非空的相同真前后缀，是0；
- AB：也没有，是0；
- ABA：两头都是 A，是1；
- ABAB：两头都是 AB，是2；
- ABABA：两头都是 ABA，是3；
- ABABAC：结尾是 C，找不到能贴住结尾的非空前缀，是0；
- ABABACA：两头都是 A，是1。

于是刚才“已经匹配 j=5 个字符”的那次失败，直接查最后一个已匹配字符的表项就行：

j = pi[j−1] = pi[4] = 3

为什么是 j−1 而不是 j？因为已经匹配的是模式第0到第 j−1 格；第 j 格正是刚才没匹配上的那个字符，不能把它算进证据里。

这张表小得可以背下来，价值却很大：搜索时一旦失配，不用回头翻旧账，直接查表就知道还能保留多长、该退到哪一格。省下的，正是第1节里那些重复确认。建表只做一次，之后每笔搜索都能反复受益。

不同教材会用 next、failure、prefix 等名字，下标和优化方式也各不相同。**先看表项的定义，再看数值。** 本文这张零起点的 pi 表，不要拿去和1977年论文里一起点、经过优化的 next 表逐格硬对。

## 7. 表怎么建？让模式和自己做同样的事

一眼看出这七个数字不难。模式很长时，能不能也免去从头检查？

能，用的还是刚才那套办法。

假设已经处理到 ABAB，它的最长相同前后缀是 AB，长度2。现在读到下一个 A，只需问一句：开头那个 AB 后面，下一个字符是不是 A？

是。两边一起接上 A，长度2就长成3。

![构造前缀表时，从AB的长度2扩展到ABA的长度3](assets/10-build-extend.png)

再遇到 C 就不一样了。当前候选边是 ABA，长度3；模式第3格是 B，和 C 对不上。

不能硬把长度3加成4。但也不必把所有更短的长度都试一遍。

ABA 自己还有一个长度1的边 A。查已经算好的表，把候选长度从3退到 pi[2]=1。现在模式第1格还是 B，仍不等于 C；继续退到 pi[0]=0，模式第0格 A 也不等于 C。所以这一格最终写0。

![为ABABAC计算表项时，候选长度依次从3退到1再到0](assets/11-build-fallback.png)

这些回退没有另发明一套算法，用的还是同一种证据：“长的接不上，就看看它还能保留哪个更短的首尾相同部分。”

这样得到的长度会形成一条严格下降的链。比如 ABABABA 的可保留长度，可以沿5、3、1、0逐级退下去。

![相同前后缀形成严格变短的回退链](assets/12-border-chain.png)

它不会原地打转，因为每次都转向更短的真前缀。

到这里你会发现，建表和搜索用的是同一套动作：能延长就延长，不能延长就查表回退。也正因如此，它不需要第二套数据结构，也不需要把模式复制一份出来。

## 8. 代码里有嵌套循环，为什么仍然是线性的？

先别数代码行，看两种动作。

一种动作是读下一个文本字符。长度为 n 的文本，只能这样往右走 n 次。

另一种动作，是把已经匹配的长度 j 调小。j 从0起步，每成功匹配一个新字符最多加1，永远不会变成负数。

于是整个搜索过程中，能退掉的长度不会超过此前涨上去的总量。一次回退有时会掉好几级，听起来很吓人，可它只会让以后还能退的次数更少——今天多退了几格，明天就少退几格，账面上的总量摆在那里。

![匹配长度像存入与取出的计数，累计回退不能超过累计增长](assets/13-amortized.png)

这叫**摊还分析**：不保证每一步花的钱一样多，而是把整段过程的总账算清楚。单看某一格，回退可能退得很深；可把整段扫描加起来，回退的总量被上涨的总量卡死，跑不出线性的框。

换个记账的比方。把 j 想成一个只进不出的存钱罐：每匹配上一个新字符就存进一格，回退时取出来花掉。罐子里的钱从来没有别人往里补，所以一辈子能取出来的总量，绝不会超过一辈子存进去的总量。至于某一次取多少，不影响这个上限。

建表也一样。扫描模式时，每读一个新字符，候选长度最多加1，回退严格把它减小。所以长度 m 的模式能在与长度成正比的时间里建好表，文本搜索同样与文本长度成正比，合起来是 O(m+n)。

O(m+n) 的意思是：在“比较和查表都算常数时间”的模型里，工作量的上界随两个长度之和增长。它不是“随便哪台机器上每个字符恰好花多少微秒”。

还有一个边界要说清：本文这个好读的 pi 版本，不保证每个新字符都在固定次数内处理完。

![一个C可以使AAAAAB模式连续回退多次，但不破坏总量线性界](assets/14-one-slow-character.png)

比如模式 AAAAAB，已经匹配五个 A 之后来了个 C，这一个 C 就可能连续撞上好几个候选位置。单步最坏延迟和整段总时间，是两个问题。原论文还讨论了更强的优化；那些优化的逐字符保证，不能顺手贴到这份教学代码上。

## 9. 把手算翻成可以运行的小程序

下面先建 pi 表，再找出所有匹配起点。建表的循环和搜索的循环长得几乎一样，都在重复同一件事：能往上加就把已经匹配的长度加一，加不动就顺着 pi 表往后退，退到能接上或者退无可退为止。空模式先作一个明确约定：它匹配文本前后以及字符之间的全部 n+1 个边界。

```python
def prefix(pattern):
    pi = [0] * len(pattern)
    for i in range(1, len(pattern)):
        j = pi[i - 1]
        while j and pattern[i] != pattern[j]:
            j = pi[j - 1]
        if pattern[i] == pattern[j]:
            j += 1
        pi[i] = j
    return pi


def find_all(text, pattern):
    if not pattern:
        return list(range(len(text) + 1))
    pi = prefix(pattern)
    hits = []
    j = 0
    for i, char in enumerate(text):
        while True:
            if char == pattern[j]:
                j += 1
                if j == len(pattern):
                    hits.append(i - len(pattern) + 1)
                    j = pi[j - 1]
                break
            if j == 0:
                break
            j = pi[j - 1]
    return hits
```

[配套实验](examples/kmp_experiment.py)保留同样的搜索步骤，并记录每次字符比较。主例得到起点[2]，搜索阶段比较12次；对应的朴素实现比较19次。40个 A 配 AAAAB 那一例，分别是76次和180次。

![同一组明确输入的字符比较计数，不是运行时间跑分](assets/15-comparison-counts.png)

这里没测墙钟时间，计数也不含建表。更不能由此宣布“自己写的 Python KMP 一定比语言内置的搜索快”：内置实现、常数开销、数据分布、是否复用同一个模式，都会影响结果。

其实在配套的 AAAAAC 与 AAAAAB 例子里，KMP 搜索比较11次，朴素方法只比较6次。可靠的最坏情况保证，不代表每一小组输入都赢。

## 10. 找到一次以后，为什么也不能随手清零？

看 AAAAA 里有多少个 AAA。

从第0、1、2格出发各有一个，彼此重叠——它们的字符互相搭着用，最后一个匹配的尾巴，恰好又是下一个匹配的开头。

![AAAAA中的AAA有三个重叠匹配，找到一个以后仍保留AA](assets/16-overlapping.png)

当我们找到第一个 AAA，它末尾的 AA 仍能当作下一次匹配的开头。所以代码记下答案后，又做了一次 j = pi[j−1]。

要是这时简单把 j 重设成0，就会丢掉本来已经知道的两个 A，也会漏掉这些重叠答案。

当然，有些应用只想要互不重叠的结果。那是另一份明确的接口约定，得另外说明，不能悄悄改变含义。

空模式也是接口约定。

![空模式在abc中的四个匹配边界](assets/17-empty-pattern.png)

本文约定 abc 中的空模式命中[0,1,2,3]。有人会选择禁止空模式，或者只返回第一个位置，都行；但调用者必须知道是哪一种。空文本配非空模式，结果就是空列表。

## 11. 日志分成几块到来，算法还认得接缝吗？

现在把主例切成三块：ABABA、BAC、ABA。

单独搜每一块，完整模式可能从一块末尾跨进下一块。这时候如果图省事，每块搜完就把状态清空、下一块从头再来，跨缝的那个答案就漏了。所以关键不在每块内部怎么搜，而在块与块之间别把已经攒下的进度扔掉。

![ABABA、BAC、ABA三个输入块用同一匹配状态连接起来](assets/18-streaming.png)

KMP 很适合保留一个很小的进度状态：模式本身、pi 表、当前已匹配长度 j，以及已经读过多少字符。新块到来接着处理就行，不必把整份历史文本重新拼起来再扫，也不必记住已经扫过的每一个字符。

配套的 StreamMatcher 对非空模式演示了这种做法。我们实际试了主例全部78种三块切分方式，包括空块，结果都保住了起点2。

这是算法状态如何跨块延续的实验，不是一套已经上线的日志系统。编码解码、网络乱序、文件轮转这些问题，仍归外层系统管。

## 12. “字符相同”，也要先说清楚

上面的 Python 字符串按 Unicode 码点逐个比较。

“看起来相同”不一定等于“码点序列相同”。比如 é 可以是一个 U+00E9，也可以由 e 加一个组合重音符号拼成。

![外观相近的é可能对应一或两个Unicode码点](assets/19-unicode-units.png)

如果想让这些写法也算同一种文字，通常要先选定一套规范化策略。规范化会改变序列和位置映射；结果下标怎么对应回原文本，也得另外设计。[Python Unicode说明](https://docs.python.org/3/howto/unicode.html)与[Unicode规范化标准](https://www.unicode.org/reports/tr15/)把这些问题分得很细。

字节、码点、用户眼里的一个字形，是不同的搜索单位。忽略大小写、允许通配符、找相似拼写，也不是照抄本文代码就自动具备的能力。换句话说，“相等”是一份得先写清楚的接口约定：换一种相等规则，同一段文本上的匹配结果就会跟着变。

![搜索合同需要明确单位、相等规则、空模式和重叠语义](assets/20-search-contracts.png)

同样，前面 O(m+n) 的讨论默认基本单位的相等比较有常数代价。要是每个“字符”其实是一棵巨大的对象树，一次相等判断本身就很贵，那份成本也得算进去，否则账就只算了一半。

## 13. 三个名字背后，是两条相遇的路

KMP 来自 Donald Knuth、James H. Morris Jr. 和 Vaughan R. Pratt 的姓氏。

1977年论文的历史章节里回顾了这样一段：1969年夏天，Morris 为 CDC 6400 编写文本编辑器，想避免让输入文件向后回退，好简化缓冲处理。另一条独立的路上，Knuth 在1970年研究 Cook 关于自动机的理论结果，从推导里提炼出实用的匹配方法；Pratt 修改了相关数据结构，让运行时间界不再依赖字母表大小，又和 Morris 一交流，两条路就接上了。

这是作者在论文里的回顾，我们没给这个故事补造现场对白或心理活动。[三位作者的1977年论文，历史章节338—339页](https://www.cs.jhu.edu/~misha/Spring23/Knuth77.pdf)

![Donald Knuth在2011年计算机历史博物馆活动上的照片](assets/knuth-2011-original.jpg)

图：Donald Knuth，Alex Handy摄，2011-01-11，Computer History Museum活动；[原文件](https://commons.wikimedia.org/wiki/File:Donald_Ervin_Knuth.jpg)，[CC BY-SA 2.0](https://creativecommons.org/licenses/by-sa/2.0/)，保留原尺寸、未修改。这不是算法产生年代的照片。

这个转折挺值得琢磨。一个需求来自“文件不要倒着读”——纯工程，甚至有点抠门；另一个来自自动机理论，纯推导。两条毫不相干的路，最后落进程序里，却都变成了很具体的状态和表：当前匹配到哪儿、失配之后退到哪儿。抽象的东西一旦真能跑起来，就变得很实在。

## 14. 最后留一道可以用手指做的题

把模式换成 ABABCAB。

先别运行程序，试着写出 pi 表；然后在 ABABCABABCAB 里找全部出现位置。

![ABABCAB的手算练习，留出前缀表与重叠结果的位置](assets/22-try-yourself.png)

可以按三个问题一步步检查：

1. 看到第五个字符 C 时，为什么此前的 AB 结构不能继续延长？
2. 找到整个 ABABCAB 后，尾部还能保留哪一段？
3. 第二个答案有没有和第一个重叠？

核对答案：pi 是[0,0,1,2,0,1,2]，匹配起点是[0,5]。完整模式首尾都有 AB，所以一次成功之后可以保留长度2，而不是忘掉全部进度。

配套程序还实际穷举了长度0—9的二进制文本、长度0—6的二进制模式，共129921对输入，与朴素搜索逐项核对。有限测试能帮忙发现实现错误，却替代不了对所有输入的证明；正确性仍来自“保留的后缀确实等于新的前缀”，效率则来自严格下降的回退与单向前进的总账。

现在再看那次失败。

B 没匹配上 C，确实排除了一个起点。但此前匹配的 ABABA 并没有白费。算法把它整理成一份还能继续用的证据，让下一次尝试站在已经知道的事情上，而不是从零重新数一遍。

KMP 最值得带走的，不是一串要背熟的数组，而是这个问题：**当一次尝试失败时，哪些信息仍然成立？**
